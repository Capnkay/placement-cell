3. The 60 second explanation

My part is the model and the business rules. Six JPA entities, mapped by Hibernate onto MySQL. An application row joins a student to a drive, with a unique key on the pair so nobody can apply twice.

The rules live in EJBs. The three services are stateless and the container wraps each write in a transaction. The shortlist basket is stateful, one per officer. A singleton starts at deploy. When an application changes, a message goes on a JMS queue and a message driven bean records it. An interceptor writes an audit row for every change, with passwords redacted. Eligibility is one plain method that lists every reason a student fails, so I can show it live.

Transactions and rollback

  • SUPPORTS: every read in the three services and all of AuditService. Join a transaction if there is one, never start one.
  • REQUIRED (default, no annotation): every write (apply, updateStatus, withdraw, save, delete, ShortlistBean.commit) and the MDB. Written out on NotificationSender.send.
  • REQUIRES_NEW: AuditWriter.write, so the audit row commits even if the caller rolls back. MANDATORY and NEVER are not used, and there is no UserTransaction anywhere.

What a rollback means. The container starts the transaction before a business method and commits when it returns. A runtime exception is a system exception: the transaction rolls back, so the INSERT or UPDATE from that call never happens, and the caller receives the original wrapped in EJBException. That is why ApplicationServlet.withdraw catches EJBException and reads getCause(). ShortlistBean.commit() therefore moves every ticked candidate or none. JMS errors are swallowed on purpose, so a broken queue never undoes an edit.

JNDI, and @EJB compared with a lookup

  • java:app/jdbc/placementDS: the pooled datasource, named in persistence.xml; PortalStatsBean gets it by @Resource and by InitialContext.lookup.
  • java:module/ShortlistBean: new InitialContext().lookup(...), ShortlistServlet line 135. The queue and its factory are java:app/jms/... names, created by annotations on NotificationSender.
  • @EJB fills a field once when the object is created, right for stateless beans. A lookup asks when you need it and gives a new stateful instance each time, so ShortlistBean is looked up and kept in the HttpSession.

JPA mapping

  • Foreign keys. The owning side has @JoinColumn and its table holds the key; the other side says mappedBy. @OneToOne StudentProfile.user owns user_id (unique). @ManyToOne Drive.company owns company_id, inverse Company.drives (@OneToMany). @ManyToOne JobApplication.student and .drive own student_id and drive_id. All four exist in MySQL.
  • No double application. JobApplication.java line 26: @UniqueConstraint(name = "uk_student_drive", columnNames = {"student_id", "drive_id"}). hasApplied is the polite check; the database rule catches a replayed POST or a race.
  • EAGER and LAZY. The three @ManyToOne links and the @OneToOne are EAGER, so a page can print application.student.user.fullName after the transaction ended. The three @OneToMany lists are LAZY and throw LazyInitializationException on a detached entity, so the beans count with queries instead.
  • Named queries. 16 are defined (for example JobApplication.exists). Three are never called: StudentProfile.byRoll, Company.byName, Drive.byCompany.

The audit trail

  • @AroundInvoke record() wraps each method of a bean with @Interceptors: ctx.proceed() (line 52), times it, hands the row to AuditWriter.
  • Reads are skipped. A name starting has, for, list, find, count, placed, statusBreakdown, search, check or ending Taken writes no row on success (lines 31, 69). A failing read is still recorded.
  • Entities print as Type#id (label(), line 117), for example StudentProfile#1, Drive#8 for apply. Strings, numbers and enums print as themselves.
  • Secrets are redacted: a parameter named password, secret, token or credential prints [redacted] (line 131).
  • The actor is always portal (line 149): sign in is by the app's own filter, so the audit does not record which officer acted.

The message driven bean path

  • Message and sender: a text string such as "Aarti Deshpande moved from Applied to Shortlisted for Lumen Health", sent by NotificationSender.send() from apply, updateStatus, withdraw and ShortlistBean.commit.
  • Consumer: NotificationMDB.onMessage() (line 43) logs "Notification delivered: ..." and saves AuditLog("notifier", "NOTIFICATION", body), after the officer's request has returned.
  • Proof: Audit page, search NOTIFICATION (actor notifier), or search server\glassfish7\glassfish\domains\domain1\logs\server.log for Notification delivered.

7. Questions you will be asked

Stateless versus stateful session bean?

Stateless keeps nothing between calls, so any pooled instance serves any caller (the three services). Stateful is one instance per client that remembers its fields (ShortlistBean).

Why is the shortlist bean stateful, and where is it held?

The officer ticks names across page loads, so the selection belongs to one person. The instance lives in the EJB container (30 minute timeout), the reference in that officer's HttpSession. A servlet field would be shared by all officers.

Singleton bean and @Startup? Interceptor?

A singleton is one instance for the whole app; @Startup creates it at deploy. An interceptor's @AroundInvoke method wraps a business method and calls ctx.proceed(), so the beans hold no audit code.

What is JNDI, and how does @EJB differ from a lookup?

JNDI is the container's name service: look up a name, get a resource, no URL or password in code. @EJB looks up once at creation; an explicit lookup gives a new stateful instance each time.

What does @PersistenceContext do?

It injects a container managed, transaction scoped EntityManager for placementPU. You never open or commit it.

Why Hibernate? JPA versus Hibernate?

JPA is the specification, Hibernate the implementation, named in persistence.xml. It writes the SQL, so only the dialect changes for another database.

Which side owns the foreign key, and how is a double application stopped?

The side with @JoinColumn, for example JobApplication.student. hasApplied checks first, and the unique key uk_student_drive refuses a second row even if the check is bypassed.

LAZY versus EAGER, and what is a detached entity?

EAGER loads the related row with the entity, LAZY waits until touched. A detached entity has lost its transaction, as in a servlet; a lazy list on it throws LazyInitializationException. merge reattaches it.

What happens when an exception is thrown inside a transaction?

A runtime exception is a system exception: the container rolls the transaction back and the caller gets it wrapped in EJBException, so the servlet reads getCause(), as withdraw does. The audit row survives (REQUIRES_NEW). Reads use SUPPORTS, writes REQUIRED.

How does the MDB work, and can a placed student apply again?

NotificationSender.send queues a text message; the container calls NotificationMDB.onMessage, which logs it and saves a NOTIFICATION row. A placed student can apply again: no rule forbids it.
