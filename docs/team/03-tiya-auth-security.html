3. The 60 second explanation

A student creates an account on the register page. The server checks every field itself, and for the email it does three things: the shape must be valid, the domain must not be a known disposable inbox, and the domain must exist in DNS and be able to receive mail. We do not send a confirmation link, so we prove the domain is real, not that the mailbox is.

The password is never stored. We store a PBKDF2 hash with 120,000 rounds and a fresh random salt for each person, so two people with the same password get different hashes. On sign in we hash what was typed and compare. A wrong password and an unknown email give the same message. Five wrong attempts lock the account for fifteen minutes.

After a good sign in we change the session id, which defeats session fixation, and keep a small user object in the session. Every page under /app and /admin goes through one filter that checks there is a user, that admin pages need the officer role, and that every POST carries a CSRF token. Every response carries a Content Security Policy, and the JSP files sit under WEB-INF so nobody can open them by URL.

7. Questions you will be asked

How is an account created?

Student self sign up only, at /register. RegisterServlet checks the CSRF token, name, email (four checks), password strength, roll number, branch, batch year, CGPA, backlogs and phone. Only if there are no errors does it call AuthService.registerStudent, which checks for a duplicate email or roll number again, hashes the password, and saves an app_user row plus a student profile. The role is hard coded to STUDENT. Officers exist only through the seeder, never through sign up.

Would it accept a fake email?

It rejects an address whose domain does not exist: test@thisdomaindoesnotexist123.com gets "That domain doesn't appear to accept email". It rejects a malformed one such as admin@campus, and 43 known disposable providers such as mailinator. It would still accept an invented mailbox at a real domain, for example asdf1234@gmail.com, because we do not check the mailbox.

So do you verify the email really exists?

Done: shape check (Validators.isEmail), disposable blocklist, and a DNS lookup for an MX record with A and AAAA as fallback (EmailDomainVerifier). That proves the domain can receive mail. Not done: no confirmation link, no OTP, no test send, and nothing proves the person owns the mailbox. That needs an SMTP account we do not have. It is the recorded next step (Security review S10). If DNS cannot be reached at all, the check lets the sign up through and logs a warning, on purpose.

Does it hide the password?

Yes on screen: the inputs are type="password" on both forms. The forms use POST, so the password is in the body, not the URL. When a form fails, the servlet forwards the page back with no password value, so the boxes come back empty. The audit trail records the call as authenticate(email, [redacted]). Honest limit: the app runs on plain HTTP on localhost, so on a real network it would need HTTPS.

How is the password stored? Can you see it?

As pbkdf2$120000$salt$hash in app_user.password_hash: PBKDF2 with HMAC SHA 256, 120,000 rounds, a 16 byte random salt per account, 256 bit output (PasswordHasher). It is one way, so we cannot read the original. Login hashes the typed password with the stored salt and compares in constant time. The salt means two people with the same password get different hashes.

What happens after wrong passwords?

Each wrong password adds one to failed_attempts in the database (AuthService lines 74 to 85). The message is "Email or password is incorrect." with HTTP 401. With two or one attempts left it adds a countdown. The fifth sets locked_until fifteen minutes ahead. While locked, even the correct password is refused. A correct sign in resets the counter. The officer can clear a lockout early on the student's page. The lock lives in the database, so restarting the server does not clear it, and it counts per account, not per computer.

Can someone tell which emails have accounts?

Not from the wrong password message: unknown email and wrong password read the same, and an unknown email still burns one hash so the timing matches. Two small leaks exist and you should say so: the countdown and lockout messages only appear for real accounts, and the register page says "An account already exists for that address".

Can a student open the admin pages?

No. AuthFilter line 63 checks the role for every path under /admin, and a student gets HTTP 403 with the "Not allowed" page. Someone not signed in is redirected to login. The path it tests is cleaned first by RequestPaths.canonical, so //admin/database and /admin;x=1/students are refused too. We tested all of these as a student. This was a real bug in an earlier version: the check read the raw URL, the container routed on the cleaned one, and a doubled slash got through. It is fixed and covered by RequestPathsTest.

What is session fixation and how do you stop it?

An attacker plants a known session id in the victim's browser, waits for the victim to sign in, then uses the same id. We call request.changeSessionId() right after a successful password check (LoginServlet line 98), so the pre login id becomes useless. Only cookies are allowed for the id (web.xml line 30), so it cannot sit in a URL.

How long does a session last, and who counts them?

30 minutes of inactivity: web.xml line 23, and SessionTracker line 24 sets the same 30 minutes when each session is created. Logout invalidates it at once. SessionTracker implements HttpSessionListener; the container calls it on creation and on invalidation or timeout, and the officer's System page shows "Sessions open now".

Which cookies do you set, and with what flags?

JSESSIONID: HttpOnly (in web.xml). remember_email (only if the box is ticked) and last_visit: HttpOnly, 30 days, path /placement, values percent encoded. portal_theme: one year, not HttpOnly, only says light or dark. No cookie holds a password. Not set: the Secure flag, because a secure cookie would never be sent over plain HTTP on localhost (accepted risk A2 in the review), and no SameSite attribute is set in our code.

Why are the JSPs under WEB-INF? Forward or redirect?

Anything under WEB-INF cannot be requested by URL: we tested /placement/WEB-INF/views/login.jsp and got 404. Only a servlet can reach a view, by RequestDispatcher.forward, which happens inside the server: the address bar keeps the servlet URL. A redirect sends the browser a 302 and it makes a second request. We forward to show a page, including a failed login, and redirect after every successful POST (Post-Redirect-Get) so refresh cannot repeat the action.

What are CSRF and the Content Security Policy?

CSRF: another site making your browser submit a form to us. Every POST needs the random per session token in a hidden field (Web.csrfValid). CSP: script-src 'self' with no inline scripts, so the browser refuses any script we did not serve. Plus frame-ancestors 'none' and X-Frame-Options: DENY against clickjacking, form-action 'self', nosniff, and no-store on every page that is not a static asset. Not set: HSTS, because we have no HTTPS.

What is not implemented (say it plainly if asked)

  • No email confirmation link, no OTP, no forgot password flow. A student who forgets a password cannot reset it by email. The change password action needs the current password (AuthService.changePassword).
  • Only the email domain is checked. The mailbox is not.
  • No HTTPS, so no Secure cookie flag and no HSTS. On a real network the password and session id would travel in clear text.
  • Lockout is per account, not per address, and the seeded demo accounts share one password (accepted risk A6 in the security review).
  • Logout works on a plain GET link, so another site could sign a user out. That is a nuisance, not a data risk.
  • The roles are two only: officer and student. There is no role management screen.
