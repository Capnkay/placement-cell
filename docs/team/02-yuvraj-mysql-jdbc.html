3. The 60 second explanation

Our Java code never contains a database URL or a password. The URL and password sit in one server file, glassfish-resources.xml. GlassFish reads it and builds a connection pool: four MySQL connections opened up front, growing to at most 24. It publishes that pool under the JNDI name java:app/jdbc/placementDS.

The code just asks the naming service for that name and gets a DataSource. It calls getConnection() and is handed a pooled connection. It runs a PreparedStatement with question mark placeholders, reads the ResultSet, and closes everything, which returns the connection to the pool.

The same datasource is used twice. Hibernate gets it through persistence.xml for normal saving and loading. My JDBC code gets it directly for reports, the database browser and a manual transaction. One pool, one set of credentials, two ways of using it.

The one place a URL and password do appear in Java is MockScoreBean.addScore, on purpose: it is our copy of the classroom practical, kept so we can compare it with the proper way.

I will show you the chain in the code, then the same rows in the browser, then in MySQL itself.

7. Questions you will be asked

Do not claim the Reports branch box proves injection safety. It is a dropdown, and ReportsServlet (line 56) uses Branches.isKnown: an unknown value is dropped and the search runs with no branch filter. The protection that matters is the ? placeholder in the DAO. Prove that with the mysql PREPARE demo (step 5) and the test parametersAreNotSql. For an in-app example use the O'Brien step on the Classroom JDBC page.

What happens if the password in the pool is wrong?

MySQL refuses the login with "Access denied for user placement_user". The password lives in one place, glassfish-resources.xml (line 52). The pool is set with ping="true", so GlassFish tests it and reports the failure. In the app, describeConnection() catches the SQLException (lines 115 to 119) and the Reports card shows "Unavailable" with MySQL's message instead of crashing. Pages that go through Hibernate will also fail. Fix the password in the XML and redeploy with .\run.ps1. No Java file changes.

What is a connection pool?

A set of already open, already authenticated MySQL connections kept by the server. Code borrows one with getConnection() and gives it back with close(). Ours (lines 41 to 47): 4 connections opened to start, at most 24, idle ones dropped after 300 seconds, and each is validated before it is handed out.

Why not open a connection per request?

Opening a TCP connection and logging in to MySQL costs far more than the query itself, and MySQL allows only a limited number of connections. A pool pays that cost once and reuses. That is exactly what MockScoreBean.addScore does wrong: it opens a new connection on every call and never closes it.

Is this safe from SQL injection? Show me.

Yes for values. Show searchCandidates lines 271 to 299: the SQL only ever gets ? added, and values are bound with setObject. Then run the mysql PREPARE demo: concatenated returns 26 rows, bound returns 0. Two honest limits. A table name cannot be a ?, so requireKnownTable (explorer, line 347) accepts only names the database itself reported, and countRows (report DAO, 426 to 437) uses a fixed list. And the classroom method is unsafe on purpose, which is why the servlet validates first.

What goes wrong with the classroom version?

Four things, all visible in addScore. It opens a new connection on every call and never closes it, so connections leak. The URL and password are in the source. The SQL is built by joining strings, so a name like O'Brien ends the string early and the statement is rejected, which is SQL injection in its everyday form. And errors are only printed: the practical hides the failure completely, ours returns 0 so the page shows an error, but the exception itself still only goes to the server log. The pooled method saves the same name because the value is bound, not joined.

What is the difference between Statement and PreparedStatement?

A Statement sends the finished SQL text. A PreparedStatement sends the SQL with ? placeholders, and the values travel separately, typed, so they can never be read as SQL. It also lets the database reuse the parsed statement. We still use a plain Statement in a few places where no user value is joined in: row counts over a fixed or database-reported table list, and the console, which runs officer typed reads behind the guard.

What if you forget to close the connection?

With a pool, close() does not close the socket, it returns the connection. Forget it and the connection is never returned. After 24 leaks the pool is empty and every request waits. That is why every connection here is in a try with resources block, and why closeDriveAndRejectPending closes in a finally.

Why JDBC for reports if you already have Hibernate?

Hibernate is right for loading an object, changing a field and saving it. Reports aggregate across tables and return numbers, never written back. Plain SQL with COUNT, GROUP BY and a LEFT JOIN is clearer than forcing it into JPQL. Both use the same datasource, so it is one pool, one set of credentials.

Explain the transaction in closeDriveAndRejectPending.

Two updates must succeed together: set the drive to CLOSED, and set its APPLIED applications to REJECTED. setAutoCommit(false), run both, commit(). On any SQLException, rollback() undoes both. The finally block restores auto commit, then closes. The bean is NOT_SUPPORTED so the container does not start its own JTA transaction, which would conflict with one driven by hand.

Can someone destroy data through the SQL console?

Three layers. One: the guard (must start with select, with, show, describe or explain, one statement, no forbidden keyword such as drop, update or into). Two: setReadOnly(true) on the connection, so the server refuses writes even if the guard were fooled. Three: the database user only has rights on placement_cell. Be honest about layer three: that user does have all privileges on this schema, so layers one and two are what stop writes here. Rows are capped at 200 and a query is cancelled after 5 seconds.

Why is the MySQL driver not inside the WAR? Do you still need Class.forName?

The pool is created by GlassFish before the application loads, so the driver must be on the server's classpath: run.ps1 copies it into domain1\lib. And Class.forName is not needed with a modern JDBC 4 driver, which registers itself. It appears in MockScoreBean.addScore only because the practical uses it.

Where is DatabaseMetaData used?

Two places. describeConnection() (report DAO, 100 to 121) fills the "live connection" card: product name and version, driver, URL, user, isolation. describe() (explorer DAO, 99 to 170) reads columns, primary keys, foreign keys and indexes for the Structure tab. tableNames() uses getTables as the whitelist.

The password is in plain text in an XML file. Is that acceptable?

It is a local database made for this project and the user only has rights on one schema. It is listed as an accepted risk in docs/SECURITY.md (item A1). The production step would be a GlassFish password alias or a secret from the environment. The point of the design is that it is in one server file, not compiled into classes.
