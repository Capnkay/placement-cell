3. The 60 second explanation

My part is everything the user touches. Pages are JSP with JSTL and EL only. Scriptlets are switched off in web.xml, so no Java can be written into a page. A servlet puts its data on the request and forwards to a JSP under WEB-INF, which is why no page can be opened by URL. Every page includes the same header and footer with the include directive, and user supplied text is printed with c:out so it is escaped.

Input is checked twice. The forms carry HTML attributes as hints, but the server decides, using the Validators class, and shows the error next to the field. All JavaScript is in one file, app.js, because our security policy forbids inline scripts. I also own two file paths in: the resume upload, limited by size, extension and the first bytes of the file, stored under a generated name and served back through a servlet; and the bulk import, which reads the request without holding a thread, using a ReadListener.

7. Questions you will be asked

Why can't I open your JSPs directly?

They live under WEB-INF/views, and the container never serves anything under WEB-INF to a browser. The only way in is RequestDispatcher.forward from a servlet, which is what Web.render does. Try it: /placement/WEB-INF/views/drives.jsp gives a 404. The one exception is index.jsp, the welcome file, and it holds no markup.

Why are scriptlets disabled, and where?

In web.xml, <scripting-invalid>true</scripting-invalid> for *.jsp and *.jspf. Java inside a page mixes logic into the view, cannot be tested, and is where injection bugs hide. With it off, a page containing a scriptlet fails to compile, so the rule cannot be broken by accident.

Include directive or jsp:include? Which do you use?

The include directive, <%@ include file="layout-top.jspf" %>. It is a static include: the fragment is pasted in when the page is translated, so the whole page becomes one servlet and variables like ctx and me set in the fragment are visible to the page. jsp:include would run at request time as a separate resource. We do not use it.

What does c:out do, and why is it on every user value?

It escapes & < > " ' before printing. Without it, a name like "><script>alert(1)</script> would be written into the page as live markup. With it, the register page sends back &#034;&gt;&lt;script&gt;alert(1)&lt;/script&gt;, which the browser shows as plain text. Plain EL like ${x} does not escape. I checked this against the running register page.

It is used inside attributes too, not only in page text. The data-confirm messages that contain a name (admin-companies.jsp line 52, admin-student-detail.jsp lines 101 and 129, my-applications.jsp line 52) use <c:out value='${co.name}'/> inside the attribute. Plain EL remains only for numbers and server made values such as ids, the csrf token and status labels. One client supplied exception: the theme cookie value on the html tag, which only the person's own browser can set.

How does a servlet hand data to a JSP?

It calls request.setAttribute("drives", drives) and then forwards. The JSP reads ${drives}. EL searches page, request, session, then application scope for the name. The address bar keeps the servlet URL because a forward happens inside the server.

Forward or redirect, and when?

Forward to show a page: same request, attributes survive, no second round trip. Redirect after a successful POST so a refresh does not repeat the write. A message that must survive the redirect goes in the session as flashSuccess or flashError, and layout-top.jspf removes it with c:remove after printing.

Is validation done in the browser or on the server?

Both, but only the server counts. Inputs carry required, min, max, maxlength, type="email", and the forms also carry novalidate, so the browser does not block a submit or show its own bubbles. Validators does the real check and the page shows the message under the field with aria-invalid="true". The register page says it plainly: "Every field is checked again on the server before anything is saved." Anyone can bypass a browser with curl.

Why is there no inline JavaScript?

The Content-Security-Policy header says script-src 'self' with no 'unsafe-inline', so the browser runs only scripts served from our own origin. An injected script tag would sit there unused. That only works if no page has a script block or an onclick, so everything is in app.js. Confirm dialogs use a data-confirm attribute and one listener. Inline styles are allowed by the policy and a few pages use them.

How does light and dark mode work?

Clicking the icon calls /theme?mode=dark. ThemeServlet stores portal_theme in a one year cookie, accepting only light or dark. Each page reads it with cookie.portal_theme.value and puts it on the html tag as data-theme. app.css line 102 swaps the colour tokens under [data-theme="dark"]. It does not follow the operating system setting.

How is the resume upload kept safe?

Four checks and one placement rule (plus a friendly message for an oversize file). @MultipartConfig caps a file at 2 MB and a request at 3 MB. The extension must be pdf, doc or docx. The first bytes must match that format (%PDF, or the zip or OLE signature). An oversize file is caught and answered with a normal message (ProfileServlet lines 73 to 82, AuthFilter lines 70 to 80). The saved name is generated (resume-1-a1b2c3d4.pdf), so the browser's file name is never used as a path. The file goes to domain1/placement-resumes, outside the deployed app, so a redeploy does not wipe it.

How is a resume served back, and can a student read someone else's?

Through /app/resume, not a static link. The servlet finds the file name from the student record, resolves it inside the upload folder only, and sends it with Content-Disposition: attachment and nosniff. A student asking for another student's id gets 403. The officer may fetch any.

Explain the non blocking bulk import in plain words.

Normally read() makes a server thread wait for the next byte, so a slow upload ties up a thread doing nothing. In BulkImportServlet the request is put in async mode (line 67) and a ReadListener is attached (line 73). The container calls onDataAvailable only when bytes are ready, we read while isReady() is true, then the thread goes back to the pool. When the body ends, onAllDataRead validates the rows, writes JSON and calls async.complete(). Limits: 512 KB and a 30 second timeout. The non blocking part is reading the request. The database work for each row still runs on that callback thread.

Is the import a file upload?

No. The officer pastes text into a box and app.js sends it with fetch as text/csv. It is not multipart, which is why it is a different mechanism from the resume upload. The CSRF token goes in the query string because there is no form body to carry it. The script writes the JSON reply into the page with textContent, never innerHTML.

What accessibility work did you do?

What is in the markup: lang="en" on every page; a label for on form fields; aria-invalid set by the server with visible error text, so colour is not the only signal; aria-hidden on the logo and icon sprite; aria-label="Menu" on the menu toggle; a visible :focus-visible outline, including on the CSS only menus; transitions only when the user has not asked for reduced motion; and a written contrast audit in the comments of app.css. Not done: no skip link, and the theme and sign out icons have title text but no aria-label.
